# temper's parts on jig's channel

Provisional, 2026-10-03, revised 2026-10-21. What temper carries on the
channel between its engine and a worker: its parts inside jig's records,
under its payload version, and a git identity's value inside a credential
grant. The channel is jig's (jig's `protocol/channel.md`), and this
document does not repeat it. It covers where temper's parts cross, the
payload version, each part field by field, a git identity's value, the
translation between the parts and the roots, the limits, and how they are
tested. What is open is listed in section 10.

## 1. In one page

- **jig's records, temper's bytes.** temper's parts ride in jig's records
  as the application's bytes, which jig's components never read (jig's
  `protocol/channel.md`, 6.2). temper's protocol layer encodes them before
  a record goes down or up, and decodes them before a root sees the
  record, so each root routes typed values only.
- **Four parts and one value:**
  - **down,** in an assignment: the workspace items, with the saved-work
    branch;
  - **up,** beside a run's answer: what the run left (the heads its
    pushes landed), what it saved, and a failed preparation's repository
    and reason;
  - **down,** with a resumed run's answered calls: each delivery's
    evidence, smith's record of the delivery's reply (section 2);
  - **beside a grant:** a git identity's value, one secret in jig's
    credential grant (section 6).
- **One codec crate,** `temper-protocol-worker-wire`, generated by
  skein's generator from a schema (skein's `codec.md`), used by the
  engine's service and the worker's, with `PAYLOAD_VERSION` (section 3).
- **Field for field.** Each record is the domain type it carries
  (`temper-worker-domain`'s `wire` types, the engine's `ForgeWorkspace`
  and `Parts`), and names a repository by the deployment's tag, down as
  up.
- **The remote is made on the engine,** from its forge's `git` base, its
  owner and its name, so workers need no forge configuration (section 4).
  So is its git, where its forge has its own: a fake forge's program,
  named in each of its repositories' items; none names the worker's.
- **Translation is small total functions** in the routing, exhaustive
  both ways, holding no state. The composed system world calls the same
  functions without the bytes between (section 7).
- **Bounded by temper's limits,** which give jig's channel the largest
  item, left and saved work, preparation and identity value, and by
  smith's, which give it the largest evidence, each within the ceiling
  jig's schema sets (section 8).

## 2. Where temper's parts cross

```
engine's root      Assignment { workspace: ForgeWorkspace, … }          Link::Up { up, parts: Parts }
  ▲                                                                       ▲
engine's routing   encodes Items; makes each remote                       decodes Left, Saved, Preparation into Parts
  ▲ jig's Part { token, bytes }                                           ▲
jig-protocol-engine-workers  ◄──── the worker's link, jig's channel ────►  jig-protocol-worker-link
  ▼ jig's Part { token, bytes }                                           ▼
worker's routing   decodes Items                                          encodes Left, Saved, Preparation
  ▼                                                                       ▼
worker's root      Event::Assign { assignment, items, save }            Request::Answer { answer, work, preparation }
```

| Part | In jig's record (jig's `protocol/channel.md`, section 5) | Way | temper's record | The engine's side | The worker's side |
|---|---|---|---|---|---|
| the workspace items | the assignment's `workspace.items` | down | `Items` | `Assignment.workspace` and the saved-work branch | `wire::Workspace` and `save` |
| what a run left | an answer's `work.left` | up | `Left` | `Parts.pushed` | `wire::Work.landed` |
| what it saved | an answer's `work.saved` | up | `Saved` | `Parts.saved` | `wire::Work.saved` |
| a failed preparation | a failed answer's `unprepared`, `permanent`'s `resource` | up | `Preparation` | `Parts.preparation` | `wire::Preparation` |
| a git identity's value | a grant's `value`, from the application's table | down | `Identity` | the identities' table | the worker's identities' table |
| a delivery's evidence | an assignment's `answered` calls: a delivery answer's `evidence` | down | smith's channel record of the delivery's reply | opaque | the worker's routing |

- **The routing encodes and decodes** with `temper-protocol-worker-wire`,
  in the step that routes the record (section 7).
- **A delivery's evidence** is the one part not in
  `temper-protocol-worker-wire`: temper's evidence is smith's channel
  record of the delivery's reply (smith's `protocol/channel.md`, section
  3), encoded and decoded with smith's codec by the worker's routing,
  and decoded on the worker against the outcome the engine committed:
  one that does not decode or disagrees refuses the start as invalid
  (`../domain/worker.md`, 4.3). The engine keeps it as bytes.

## 3. The payload version

- **`PAYLOAD_VERSION`,** in `temper-protocol-worker-wire`, covers every
  encoding of temper's carried on the channel: the workspace items with
  the saved-work branch, the left and saved work, the preparation, a git
  identity's value, and a delivery's evidence, smith's record as the
  smith temper links encodes it.
- **Checked at the opening.** The services give it to both channel
  components as they make them, and a worker whose credential names
  another is refused before any part crosses (jig's
  `protocol/channel.md`, 4.1).
- **It stays at 4 until the first release.** A change to one of these
  encodings, including a repin of smith that changes the delivery's
  record, changes the schema, generated code and one set of golden bytes
  in place. The version moves at a release (`README.md`, section 9;
  skein's `codec.md`, section 5). An engine and its workers come from
  the same build, and nothing is translated between versions (jig's
  `protocol/README.md`, section 7).

## 4. Down: the workspace items

The assignment's `workspace` (jig's: the workstream and the items) is
present exactly when the run has a repository; its items are one
`Items` record. A run with none, a chat for one, has no workspace and no
part (`../domain/worker.md`, 4.1).

In the schema's terms (each byte field and list has its limit, section
8; enums are numbered in this order):

```
record Items       { repositories: list Repository  save: option bytes }
record Repository  { tag: u64  name: bytes  remote: bytes  git: option bytes  start: Start  access: Access  identity: u32  account: option u64 }
enum   Start       { merge: Merge, base: Branch, branch: Branch, commit: Commit, saved: Branch }
record Merge       { branch: bytes  base: fixed 32 }
record Branch      { branch: bytes }
record Commit      { commit: fixed 32 }
enum   Access      { writable: Writable, read_only }
record Writable    { push: bytes  expected: option fixed 32  landing: option bytes }
```

| Field | From the engine (`ForgeRepository`) | To the worker (`wire::Repository`) |
|---|---|---|
| `tag` | `tag`, the deployment's tag: the forge's number and the repository's id, packed (`../domain/forge.md`, section 4) | `tag`, echoed in what landed |
| `name` | `name` | `name`: the directory, one path component, unique in the workspace |
| `remote` | made: the `git` of the configured forge whose number is `provider.forge`, `/`, `owner`, `/`, `name`, `.git` (configuration.md, section 3) | `remote`, never interpreted by the domain; the git component's URL (git.md, section 3) |
| `git` | made by the routing: the `git` of the setup entry faking the forge whose number is `provider.forge`, resolved to an absolute path (setup.md, 8.2); none for every other forge | `git`, never interpreted by the domain; the program the git component runs for every operation on the repository, and `workers[].git` for none (git.md, section 3) |
| `start` | `ForgeStart::Base`, `Branch`, `Saved`, `Merge { branch, base }`; the engine never asks for a commit | `Start`, all five |
| `access` | `push: Some(branch)` is `writable { push: branch, expected: none, landing }`; `landing` is the change's landing branch only for an inherited writable producer starting on its push branch; `None` push is `read_only` | `Access`; landing is bounded by the branch-name limit |
| `identity` | `identity`: the number of the forge's git identity, the credential jig grants the attempt (credentials.md, section 4) | `identity`, the grant's number in the application's table |
| `account` | made by the routing, on a GitHub forge: the `account` of the entry in the forge's identity value, as the routing last made it (section 6), whose `account_login` equals `owner`, compared ASCII case-insensitively; none when no entry matches, and none on Forgejo | `account`, by which the worker's routing picks the identity's entry for each git operation on the repository (section 6) |
| `save` | the saved-work branch, when the root asks for a save | `save` beside `Event::Assign` |

- **Ids** are the full object id in 32 bytes: a SHA-256 id as it is, a
  SHA-1 id followed by twelve zero bytes (git.md, section 3).
- **Existing producer work.** `landing` is independent of `start` and
  `expected`. The worker fetches its tip once per hold, and an unchanged
  head not contained in it is delivered through an actual guarded push
  (`../domain/worker.md`, section 5). A missing landing branch fails
  preparation. This field changes only fresh assignments; stored heads,
  receipts, delivery evidence and resumed conversations keep their encoding.
- **Saving.** The engine's routing sets jig's `save` and temper's `save`
  together, both or neither; the worker's root saves only when both say
  so, and never for a workspace that starts a merge
  (`../domain/worker.md`, 4.2).
- **The remote and the git** are the fields the routing makes rather
  than copies; everything a worker needs to reach the forge, but the
  credential, is in them. The credential is the grant's (section 6).
- **A fake forge's git is local.** Its program is a path on the
  engine's machine, so a fake forge serves workers on that machine
  alone, as its listener is loopback's (setup.md, 8.4): standalone's
  worker, and the cluster's workers alone (README, 15.2). A worker on
  another host takes its own machine's git for every repository
  (configuration.md, section 4).
- **Checked at the worker's entrance:** names, remotes, programs and
  branches within its limits, a program that is not an absolute path,
  and a repository named twice are refused as an
  invalid start that names the item (`../domain/worker.md`, 4.1), as are
  items that do not decode (section 7).

## 5. Up: what a run left

What a run left, what it saved and why its workspace could not be
prepared go beside its answer, in jig's answer record: `left` and
`saved` in the answer's work (ended, parked or failed), and the
preparation in a failed answer whose preparation is permanent. A
refusal carries none. Each names a repository by its tag.

```
record Left             { landed: list Landed }
record Landed           { tag: u64  commit: fixed 32 }
record Saved            { repositories: list SavedRepository }
record SavedRepository  { tag: u64  from_saved: bool  landing: Landing }
enum   Landing          { conflicted: Files, explained: PushFailure, landed: Commit,
                          moved, failed, refused, unchanged }
record Files            { files: list bytes }
record PushFailure      { repository: option u32  reason: PushReason  diagnostic: Diagnostic }
enum   PushReason       { missing_repository, missing_branch, missing_commit, refused,
                          unreachable, broken, timed_out, cancelled, unavailable, busy,
                          too_large, nothing, unknown }
record Diagnostic       { output: bytes  cut: u64 }
enum   Preparation      { transient, missing: Missed, refused: Tag }
record Missed           { tag: u64  missing: Missing }
record Tag              { tag: u64 }
enum   Missing          { repository, branch, commit }
```

- **`Left`** is `wire::Work.landed`: each repository a run's pushes
  landed in, by tag, ascending, with the last commit landed there, the
  head a pull request is to show.
- **`Saved`** is `wire::Work.saved`: each repository's outcome of the
  save, in the assignment's order, with its tag and whether it started
  from saved work; each `Landing` field for field, its diagnostic the
  checkout's `PushDiagnostic` (at most `PushDiagnostic::CAPACITY` bytes
  and the count dropped before them).
- **`Preparation`** is `wire::Preparation`, the repository named by its
  tag. The worker's routing sends it only for a permanent failure, as
  jig's `permanent`'s resource; a transient one has no resource in jig's
  record, and jig's class says it.
- **By tag, never by place.** The engine's routing holds no state, and an
  answer may reach an engine that restarted since it made the
  assignment, so a part must name its repositories itself. The worker's
  root keeps each run's items, tags and starts included, until the
  engine has its answer, and names each repository of `Saved` and
  `Preparation` by its tag, with whether it started from saved work.
  `PushFailure`'s `repository` stays the domain's own, a place, which the
  engine never reads.
- **Into the engine's `Parts`:**
  - `pushed`: each `Landed`, as `forge::Pushed { tag, commit }`;
  - `saved`: absent without a `Saved` part, which keeps the previous set;
    with one, the tags of the repositories with saved work after the
    save: those whose landing is `landed`, and those that started from
    saved work and whose save left that branch as it was;
  - `preparation`: from `missing`, the repository's tag and what the
    forge lacks; from `refused`, its tag and that the forge refused the
    identity. The root reports them as a fact of the attempt
    (`../domain/root.md`, 7.4).

## 6. A git identity's value

One secret of jig's credential grant (jig's `protocol/channel.md`,
section 8), from the application's table:

```
record Identity { kind: Kind  login: text  name: text  email: text }
enum   Kind     { forgejo: Token, github: Entries }
record Token    { token: secret }
record Entries  { entries: list Entry }
record Entry    { account: u64  account_login: text  token: secret }
```

- **Versioned twice:** by `PAYLOAD_VERSION` (section 3), and by its
  kind, so a worker tells Forgejo's value from GitHub's before it reads
  a token.
- **Forgejo's** is one token, the forge's `GitToken` record, with the
  bot's login, the `User` record's (credentials.md, 2.1 and section 4).
- **GitHub's** is a list of entries, one per installation with a
  token, at most `forges.installations` (configuration.md, section 7),
  in the order of their installations' ids: the installation's account
  id and login, and its token. The tokens are those the GitHub forge
  mints, held in memory only and never stored; the login is
  `x-access-token`. No entry carries its expiry: the grant's validity,
  the earliest of them, bounds the value whole (credentials.md, section
  4).
- **Its other fields** are configuration's or the forge's defaults
  (configuration.md, section 3): the login, and the author's name and
  email, by default on GitHub the bot's, `<slug>[bot]` and
  `<id>+<slug>[bot]@users.noreply.github.com`, `<slug>` the `AppSlug`
  record's and `<id>` the `User` record's. The login holds no `:` and no
  control byte; the name and the email are not empty and hold no NUL,
  newline, `<` or `>`.
- **Generations.** Each change of value is a new generation, strictly
  increasing per number: a Forgejo forge's `GitToken` replaced; on
  GitHub, each change of its entries, a token minted or renewed, or an
  installation deleted, suspended or no longer accepted (forge.md, 2.5).
  Generation 1 at each start, on GitHub at the forge's first
  `Connected` (credentials.md, section 4).
- **On the engine:** the routing encodes the value at start and at each
  new generation into the identities' table, as one secret held by
  number and generation, the two newest kept (credentials.md, section
  4); `jig-protocol-engine-workers` fills it in as a grant's `value`,
  through the routing, with an empty `account_id`.
- **On the worker:** `jig-protocol-worker-link` takes the value out with
  its table, the application's, its number and generation; the routing
  decodes it and keeps it in the worker's identities' table, at most the
  two newest generations of each, so that a push in flight across a
  change ends on the value it began with. With each operation that names
  the identity, the routing hands the git component one token, its login
  and the author (git.md, sections 2 and 5): Forgejo's token, or on
  GitHub the entry whose `account` is the repository's item's `account`
  (section 4). With no such entry the operation fails `Refused` without
  running git, named "temper's App is not installed on the account
  owning <name>", `<name>` the item's (section 4). A
  value that does not decode, or breaks a field's rule, is dropped and
  counted; an operation that needs it fails `Broken`.
- **Shown nowhere.** The record's `Debug` shows each token's length only
  (skein-lib's `Secret`, the schema's `secret`); the login and the author
  are not secret. No root, fact, store record or log holds the value.
- **Its size** must fit jig's bound on a grant's value (section 8), which
  configuration checks for every identity at start; a GitHub forge's
  grows with `forges.installations`. A GitHub entry's token is bounded
  by the forge component's `token_bytes` (configuration.md, section 7),
  not by Forgejo's token's bound, so that the list fits jig's bound.

## 7. Translation

Small total functions in `temper-service`, its engine module and its
worker module, between temper's records and the roots' types, called by
the routing in the step that routes the record:

| Side | Function | From | To |
|---|---|---|---|
| engine | items | the root's `Assignment` (its workspace, its saved-work branch) and the configured forges' `git` bases | `Items`, or none for an empty workspace |
| engine | parts | `Left`, `Saved`, `Preparation`, each if present | `Parts` |
| engine | identity | the forge's records (Forgejo) or the GitHub forge's minted installation tokens (in memory), with the identity's configured login and author | `Identity`'s bytes |
| worker | workspace | `Items`, or none | `wire::Workspace`, `save` |
| worker | work | `wire::Work`, with each repository's tag and start | `Left`, `Saved` |
| worker | preparation | `wire::Preparation`, with the repository's tag | `Preparation`, or none for a transient one |
| worker | value | a grant's value | an identity for the worker's identities' table |

- **Total and exhaustive both ways:** each matches every variant of what
  it reads, with no wildcard, so a variant added on either side fails to
  build until it is translated. No function reads io, keeps state or
  decides: what the domain does with a part is the domain's.
- **Bytes only through the generated codecs.** A part's record is
  encoded measured (skein's `codec.md`) and decoded against the side's
  limits.
- **A part that does not decode,**
  - on the engine: the root gets the answer with no parts
    (`Parts::none()`), as it does for parts beyond its bounds; the
    routing counts it. A worker of the same payload version never sends
    one.
  - on the worker: items that do not decode reach the root as such, and
    the root refuses the start as invalid, naming the workspace items,
    as it refuses items beyond its limits (`../domain/worker.md`, 4.1).
- **The composed system world** (`tests/system`, `composed/link.rs`)
  calls these functions, each record passed from the encoding side to the
  decoding side without its bytes, in place of its own translation of
  assignments and answers. So the domain tier and the protocol layer
  translate alike, and drift is a build error on either.

## 8. Limits

- **temper's largest parts, given to jig's worker wire's sizes** (jig's
  `protocol/channel.md`, section 11), each the generated codec's worst
  case under the side's limits:

  | jig's size | temper's largest | From |
  |---|---|---|
  | `items` | `Items` | the engine: the forge's `resources_per_task` and `name_bytes`, the longest configured `git` base and the longest fake forge's program; the worker: the checkout's `repositories` and `name_bytes`, and 4,096 bytes per program, Linux's `PATH_MAX` |
  | `left` | `Left` | the checkout's `repositories` |
  | `saved` | `Saved` | the checkout's `repositories`, `conflicts` and `path_bytes`, and `PushDiagnostic::CAPACITY` |
  | `resource` | `Preparation` | fixed |
  | `evidence` | smith's delivery reply | smith's channel limits, as the hub's `delivery_evidence_bytes` takes them |
  | `grant` | max(credential value bound, program source name bound 32, generated `Identity::worst_case_bytes`), which grows with `forges.installations` on a GitHub forge | jig's accounts (jig's `protocol/llm.md`, section 6); configuration's identities, `records.value_bytes` and `forges.installations`, checked to fit jig's grant bound at start (configuration.md, section 3) |
  | `credentials` | the number of git identities | configuration (configuration.md, section 3) |

- **Within jig's ceilings.** Each must fit the ceiling jig's schema gives
  its field; `temper serve` refuses a start whose limits pass one, naming
  the limit.
- **Credential capacity.** The engine uses max(`accounts.token`, jig's 4,096-byte
  key ceiling) when a configured provider offers keys. The worker has no
  provider declarations and reserves that key ceiling unconditionally.
  Tables and frames use those same bounds. Startup checks the engine's bound against the worker's
  table, and the worker's against smith's credential and withdrawn bodies;
  a source name must fit smith's program body too. No wire length is
  counted by hand. Channel sizes use each side's own limits.
- **The engine's within the worker's.** Each side computes its sizes from
  its own limits, and jig's terms compare them at the opening (jig's
  `protocol/channel.md`, 4.1). In one process both are known at start,
  so `temper serve` refuses limits under which the engine could send an
  item larger than the worker takes, rather than a link that never
  opens.
  A worker started alone takes a GitHub value's entries and an entry's
  token at the defaults of `forges.installations` and
  `forge_component.token_bytes`, and the worker in the engine's process
  takes the engine's; an engine whose limits pass a worker's is refused
  at the opening.
- **The remote fits the worker's names.** The longest remote the routing
  can make, the longest `git` base, two `/`, an owner and a name of the
  forge's `name_bytes` and `.git`, must be within the checkout's
  `name_bytes`, and so must the forge's names and branches; otherwise the
  start is refused, naming the limit. A fake forge's program, resolved,
  is at most 4,096 bytes, or the start is refused, naming its path.
- **Memory:** the routing holds a part only while it encodes or decodes
  it, within the codec's worst case; the identities' tables hold one
  value per identity and generation, at most two generations on a worker.

## 9. Testing

Within the suites' budgets (`../domain/testing.md`, section 2):

- **Step tests in `temper-protocol-worker-wire`,** those skein's
  `codec.md`, section 6 generates for each record, and `Identity`'s
  `Debug` holding no byte of its tokens, of either kind. Golden bytes fail when an
  encoding changes, which is when `PAYLOAD_VERSION` moves.
- **Step tests of the translation** in `temper-service`: each function
  both ways for every variant; an engine's workspace through `Items` to
  the worker's, field for field, with its remote made from the base, the
  owner and the name; the heads a run landed reaching `Parts.pushed`; a
  save naming each repository with saved work after it (the two cases
  `composed/link.rs`'s own tests hold); each preparation reaching
  `Parts.preparation`; a part that does not decode, on each side.
- **Fuzz targets,** in the fuzzy suite: each record's decoder, on
  arbitrary bytes and on mutated golden bytes.
- **Through bytes,** the one-process world carries every part on jig's
  channel joined in process: each story that prepares a workspace,
  pushes, saves or fails to prepare (`../domain/testing.md`, 2.5). jig's channel
  worlds carry them as opaque bytes, and need nothing of temper's.
- **Without bytes,** the composed system world runs the same functions
  (section 7).

## 10. Open questions

- **Where a delivery's evidence is made.** The worker decodes it from a
  resumed run's answered calls; which side encodes it as the core
  commits a delivery follows jig's settled calls. Default: the side that
  hands the core the delivery encodes smith's record, with smith's codec,
  under the payload version.
- **Large workspaces.** Items cross in one part, within one assignment's
  frame. If workspaces grow to many repositories, the items could cross
  as records of their own after the assignment. Default: one part.
